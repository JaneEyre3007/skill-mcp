# 反模式清单

这份清单从外部逆向 skill 的反模式文档中抽取高价值部分，并改写为当前 `env-patch` 适用的版本。

## 1. 用浏览器结果当最终方案

错误表现：

1. 用浏览器过挑战拿 cookie
2. 再把 cookie 硬编码进最终脚本
3. 或者每次请求前都靠浏览器跑一遍

为什么错：

1. 浏览器应该是分析工具，不是最终依赖
2. 这种方案一旦 cookie 过期就失效
3. 与“纯 Node.js 可运行”的最终目标冲突

正确方向：

1. 还原 cookie / 签名生成逻辑
2. 或在 Node 里复现最小环境执行原始逻辑

## 2. 关键值硬编码

错误表现：

1. 把 `sign`、`cookie`、`__ac_signature`、挑战结果写死
2. headers 文件里塞整段浏览器抓包结果

为什么错：

1. 这不是还原，只是缓存一次结果
2. 一旦过期或换账号就失效

正确方向：

1. 只允许把样本作为对照
2. 最终脚本必须自己生成关键动态值

## 3. 已有同站点目录还从零重做

错误表现：

1. 工作区明明已有旧脚本、旧目录、旧案例
2. 仍然重建新项目从零补环境

为什么错：

1. 容易重复踩坑
2. 容易错过已经验证过的关键经验

正确方向：

1. 先读已有目录和样例
2. 把旧代码当“踩坑记录”和“事实样本”复用

## 4. 遇到复杂 SDK 就断言无法协议化

错误表现：

1. 看到 JSVMP、SDK、瑞数 challenge 就直接说“只能浏览器跑”

为什么错：

1. 复杂不等于不可还原
2. 很多场景只是路径没选对

正确方向：

1. 先按降级梯度走
2. 先试最小环境、vm、jsdom、WASM 对应路径

## 5. 一上来就全量补环境

错误表现：

1. 不看访问日志，不看诊断报告
2. 直接堆大量 API 和属性

为什么错：

1. 成本高
2. 噪音大
3. 反而更容易引入假差异

正确方向：

1. 先修致命级
2. 再修实际访问到的高危级
3. 中危级只在命中时补

## 6. 瑞数 challenge 类目标上大范围开 Proxy 不收缩

错误表现：

1. 整个 `window`、`document`、大量子对象全部开 Proxy
2. 代码卡死、极慢、空转后仍不调整

为什么错：

1. 日志和代理本身会改变运行时特征
2. 还会放大反调试或性能问题

正确方向：

1. 先关掉大范围日志代理
2. 只保留关键对象和关键方法监控

## 7. 报告和日志都不看，直接猜

错误表现：

1. 看到某字段常见，就先补
2. 没验证它是否真的参与校验

为什么错：

1. 浏览器里也可能是 `undefined`
2. 你可能在修一个根本不影响结果的点

正确方向：

1. 先看 `ERRORS / UNDEFINED / CALLS`
2. 再看定向日志
3. 用结果变化验证补丁是否真有效
